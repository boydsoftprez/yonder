# M1b-1 Console Spine Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Put a Node-RED console on the device, reachable over the access point, that **offers nothing but setting an administrator password until one is set** — and, once set, gates every write path and the flow editor behind it.

**What this milestone deliberately does not build:** any console *page*. No status readout, no network form, no themes, no activity log. Those are M1b-2. This milestone builds the thing they will be served from, and the lock on the front of it. The exit criterion below is reachable with zero flows installed, which is the point: in setup mode there are no flows, so there is provably no function to reach.

**Architecture:** `settings.js` is **generated**, never hand-written — a `ConsoleRenderer` implements the `Renderer` interface the apply engine already accepts, so `ui.*` changes inherit M0's validate → snapshot → apply → confirm-or-revert cycle for free, exactly as `NetworkRenderer` did for `network.*`. The console runs as an unprivileged `yonder` user and holds **no credential at all**: the administrator password hash never leaves root-owned `secrets.yaml`, and the console asks the daemon over the Unix socket whether a submitted password is correct. That socket becoming reachable by a non-root console is K-01, which this milestone closes.

**Tech Stack:** Node 24 LTS · TypeScript · Zod · vitest · Node-RED 5 · `@flowfuse/node-red-dashboard` 1.x · `node:crypto` scrypt · POSIX `sh` (installer)

## Design decisions this plan makes

These are settled here so the tasks below can just refer to them. Task 9 records the first as ADR-0008.

### The setup gate is enforced by absence, not by hiding

R-SEC-09 says the console "offers no function but setting one". A dashboard whose pages are hidden by a UI conditional does not satisfy that — the routes still exist and still answer. So:

| | Unprovisioned (no admin password in secrets) | Provisioned |
|---|---|---|
| Flows loaded | **none** — empty flows file | `flows/flows.json` (M1b-2) |
| Editor (`httpAdminRoot`) | `false` — not mounted at all | `/editor`, behind `adminAuth` |
| What is served | one static page, one `POST`, nothing else | the console, behind a session |
| Reads config? | no route exists that can | yes, authenticated |

In setup mode there is no flow, so there is no node, so there is nothing to call. The property is structural rather than enforced.

### The console holds no credential

The console runs as `yonder`. `secrets.yaml` is `0600 root`. The console therefore *cannot* read the password hash, which is the desired state. Authentication is a question it asks the daemon:

```
console --(POST /admin/verify {password})--> daemon (root) --> scrypt compare --> {ok: true|false}
```

The hash never leaves root. A console compromise yields no offline-crackable material. `adminAuth.authenticate` and the dashboard session middleware both go through this one route.

### Password hashing is `node:crypto` scrypt, not bcrypt

`bcrypt` is a native module needing a compiler on the target — unacceptable on an offline arm64 install. `bcryptjs` is pure JS but is another vendored dependency. `crypto.scrypt` is in Node, is designed for exactly this, and costs nothing to ship. Stored form:

```
scrypt$<N>$<r>$<p>$<base64 salt>$<base64 hash>
```

Comparison uses `timingSafeEqual`. Parameters are recorded in the string so they can be raised later without invalidating existing hashes.

### Sessions are in-memory and die with the process

The console mints a random signing key at start-up. A console restart logs everyone out. That is correct for a device that restarts its console when its configuration changes, and it means there is no session secret at rest.

## File Structure

```
packages/yonder-core/src/console/
├── password.ts          pure: scrypt hash/verify, the stored-form codec
├── credential.ts        the admin credential, over SecretStore
├── throttle.ts          pure: failed-attempt backoff
├── client.ts            the console's client for the daemon socket
├── session.ts           pure: signed session tokens, in-memory store
├── middleware.ts        Express middleware: login gate + the setup POST
├── settings.ts          pure: Config -> the text of settings.js
├── renderer.ts          ConsoleRenderer implements Renderer
└── assets/
    └── setup.html       the one page setup mode serves

installer/
├── make-payload.sh      builds vendor/ for a target arch (node + node-red)
└── roles/30-console.sh  offline install, unit, post-conditions

systemd/yonder-console.service
```

**Responsibility boundaries.** `password.ts` knows hashing and nothing else. `credential.ts` knows where the hash lives. `session.ts` and `throttle.ts` are pure and clock-injected. `middleware.ts` orchestrates and does no crypto of its own. `settings.ts` is pure translation, `Config` in and a string out — that is where most of the tests live. `renderer.ts` only writes and restarts.

## Task 1: scrypt password hashing

**Requirements:** R-SEC-09, R-SEC-10

**Files:** Create `src/console/password.ts`, `src/console/password.test.ts`

- [ ] `hashPassword(plain: string): string` — 16-byte random salt, `N=16384, r=8, p=1`, 32-byte output, returns the stored form above.
- [ ] `verifyPassword(plain: string, stored: string): boolean` — parses the stored form, re-derives with *its* recorded parameters (not the current defaults), compares with `timingSafeEqual`.
- [ ] A malformed or unrecognised stored form returns `false`. It must never throw: a corrupt `secrets.yaml` entry must lock the operator out with a wrong-password message, not crash the daemon on every login attempt.
- [ ] `verifyPassword` returns `false` for an empty plaintext regardless of the stored value.
- [ ] A minimum length is enforced at the point of *setting* (Task 3), not here.

**Tests:**
- [ ] A hash verifies against its own plaintext and fails against a different one.
- [ ] Two hashes of the same plaintext differ (salt is random).
- [ ] A stored form with non-default `N`/`r`/`p` still verifies — parameters are read from the string.
- [ ] Garbage stored forms — `""`, `"x"`, `"scrypt$$$$"`, a bcrypt-looking string, a stored form with a truncated salt — all return `false`, none throw.
- [ ] The stored form contains no substring of the plaintext.

**Verify:** `npm test`

## Task 2: the `yonder` account, and the socket the console can reach — closes K-01

**Requirements:** R-SEC-04, K-01

The daemon must keep running as root: it drives NetworkManager. What changes is its *group*, so that the runtime directory and socket it creates are reachable by a console that is not root.

**Files:** Modify `systemd/yonder-core.service`, `installer/lib/common.sh`, `installer/roles/10-base.sh`

- [ ] `installer/roles/10-base.sh`: create a system group `yonder` and a system user `yonder` (no login shell, home `/var/lib/yonder`, member of group `yonder`). Idempotent — re-running the installer must not fail on an existing account. Use `getent` to test before creating.
- [ ] `systemd/yonder-core.service`: add `Group=yonder`, `RuntimeDirectory=yonder`, `RuntimeDirectoryMode=0750`. No `User=` — the daemon stays root, and with `Group=yonder` systemd creates `/run/yonder` as `root:yonder 0750` and the socket the daemon binds inherits that group. The existing `chmodSync(socketPath, 0o660)` in `server.ts` then makes it group-writable. **Do not chown from code** — the unit is the one place this is expressed.
- [ ] `installer/lib/common.sh`: add `assert_unit_accounts <unit-file>` — for each `User=` and `Group=` in the unit, verify the account exists with `getent passwd`/`getent group`. A unit naming a group that does not exist fails to start with `217/USER`, and for `yonder-core` that means **no network at all**. This is the same class of defect `assert_unit_exec` was written for, and it is load-bearing against rule 6.
- [ ] Call `assert_unit_accounts` in `20-yonder-core.sh` alongside the existing `assert_unit_exec`, before anything is enabled or started.
- [ ] On a dry run, `assert_unit_accounts` reports what it would check and returns success, matching `assert_unit_exec`'s split.

**Tests:** `shellcheck` clean. Exercise `assert_unit_accounts` against a unit naming a nonexistent group and confirm it dies with a reason naming the group.

**Verify:** `shellcheck installer/install.sh installer/lib/*.sh installer/roles/*.sh` and `installer/install.sh --dry-run`

## Task 3: the admin credential and the daemon routes that own it

**Requirements:** R-SEC-04, R-SEC-09, R-SEC-10

**Files:** Create `src/console/credential.ts`, `src/console/throttle.ts` and their tests. Modify `src/daemon/routes.ts`, `src/daemon/routes.test.ts`

- [ ] `credential.ts`: `AdminCredential` over `SecretStore`, secret name **`admin_password`**. Methods: `isSet()`, `set(plain)`, `verify(plain)`. `set` refuses when one is already set and returns a distinguishable result — first-run is a one-way step, and a device that lets an unauthenticated caller *replace* the password has no lock at all. Changing a known password is a later, authenticated operation and is out of scope here.
- [ ] `set` enforces a minimum length of 8 characters and rejects an all-whitespace value. Reject with a message that says the rule and **never echoes the value**.
- [ ] `throttle.ts`: pure, clock-injected. Counts consecutive failures and reports a delay-or-refuse decision. After 5 consecutive failures, refuse for 60 seconds; a success resets the counter. No unbounded growth: keyed by nothing (there is one administrator), so it is a single counter, not a map.
- [ ] `routes.ts`: add
  - `GET /console/state` → `{ provisioned: boolean }`. **The only route reachable before provisioning.** It returns nothing else — no version, no hostname, no config.
  - `POST /admin/password` `{password}` → sets it, once. `409` when already set. `400` when it fails the length rule.
  - `POST /admin/verify` `{password}` → `{ ok: boolean }`, throttled. Returns `429` with a `retryAfter` when refused.
- [ ] **Every one of these routes must redact the password before anything is logged.** Extend the existing redaction rather than adding a second mechanism — R-SEC-10 says redaction happens where the value is captured.
- [ ] `GET /config`, `POST /apply` and `POST /confirm` must **refuse with 403 while unprovisioned**. The console cannot reach them anyway in setup mode, but the socket is the boundary, not the console, and R-SEC-09 says *no configuration read*.

**Tests:**
- [ ] `set` then `isSet` is true; a second `set` refuses and leaves the first hash intact.
- [ ] `verify` true for the right password, false for the wrong one, false when none is set.
- [ ] Short and whitespace-only passwords are refused, and the refusal message does not contain the submitted value.
- [ ] Throttle: 5 failures then refuse; the clock advancing 60 s re-allows; a success mid-sequence resets.
- [ ] Routes: `GET /config` is 403 while unprovisioned and 200 after; `POST /admin/password` is 409 the second time; `POST /admin/verify` is 429 after the threshold.
- [ ] **No test may find the plaintext in any captured log line.** Assert on the captured `warn`/`log` output directly.

**Verify:** `npm test`

## Task 4: the console's client, sessions, and the middleware that is the gate

**Requirements:** R-SEC-04, R-SEC-05, R-SEC-09, R-UI-01, R-UI-02

**Files:** Create `src/console/client.ts`, `src/console/session.ts`, `src/console/middleware.ts`, `src/console/assets/setup.html`, and tests for each.

- [ ] `client.ts`: a small HTTP-over-Unix-socket client for the routes in Task 3. Injected socket path. Every failure mode — socket absent, connection refused, malformed reply, timeout — resolves to a typed error, never a throw that would take Node-RED down. **A daemon that is not answering must present as "cannot verify", not as "authenticated".** Fail closed.
- [ ] `session.ts`: pure and clock-injected. `mint()` returns an opaque token; `check(token)` validates against an in-memory set with an idle expiry (default 12 h). The signing key is generated per process. `revokeAll()` for completeness.
- [ ] `middleware.ts`: Express middleware, exported as two factories.
  - `setupMiddleware(deps)` — mounted when unprovisioned. `GET /` serves `assets/setup.html`. `POST /setup` relays to `POST /admin/password`, and on success returns a page saying the console is restarting. **Every other path returns 404.** Not a redirect to a login page — a 404, because nothing else exists.
  - `consoleMiddleware(deps)` — mounted when provisioned. No session cookie → serve the login page. `POST /login` → `POST /admin/verify`, and on success sets an `HttpOnly`, `SameSite=Strict` cookie (`Secure` is *not* set: the access point is plain HTTP and a `Secure` cookie would silently never be sent — note this in a comment, and in Task 9's docs, as the known limitation it is).
  - `POST /logout` clears it.
- [ ] `assets/setup.html`: one self-contained page. **No asset fetched from the internet** (R-UI-01) — no CDN font, no external stylesheet, no analytics. Inline CSS, no framework. It states plainly that the access point passphrase is a published default and that this password is the real lock (ADR-0007), and it must not describe the passphrase as a secret.
- [ ] The page is day-themed (R-UI-07's default). Full theming is M1b-2; this page just must not be dark.

**Tests:**
- [ ] Setup middleware: `GET /` serves the page; `GET /anything-else` is 404; `POST /setup` with a valid password calls the client once; with a short one, returns the daemon's 400 and does not retry.
- [ ] Console middleware: no cookie → login page, not the console; a wrong password does not set a cookie; a right one does; the cookie is `HttpOnly` and `SameSite=Strict`.
- [ ] **A daemon that is down produces a failed login, never a successful one.** Test with a client stubbed to every failure mode.
- [ ] Sessions expire on the injected clock; a token from a different key does not validate.
- [ ] The setup HTML contains no `http://` or `https://` reference to an external host. Assert this as a test, not as a review habit — it is R-UI-01 and it is easy to regress.

**Verify:** `npm test`

## Task 5: `settings.js` is generated, and the console is a renderer

**Requirements:** R-SEC-05, R-CFG-03, R-UI-01, and CLAUDE.md rule 2

**Files:** Create `src/console/settings.ts`, `src/console/renderer.ts`, and tests. Modify wherever `buildRenderers` is assembled.

- [ ] `settings.ts`: pure. `renderSettings(config, {provisioned, paths}): string` produces the text of `settings.js`. It must set:
  - `uiPort` from `config.ui.port`, `uiHost: "0.0.0.0"`
  - `userDir: /var/lib/yonder/console`, `flowFile` — the empty setup flows file when unprovisioned, `flows.json` when provisioned
  - **`functionExternalModules: false`**
  - **`nodesExcludes`** listing the `function` node and the `exec` node. Both are code-execution surfaces; rule 2 forbids the first outright and R-SEC-05 covers the second.
  - `httpAdminRoot: false` when unprovisioned; `"/editor"` with `adminAuth` delegating to the daemon when provisioned and `config.ui.editor.enabled`
  - `httpNodeMiddleware` wired to the middleware from Task 4
  - `logging.console.level: "info"`, and **no `audit` of request bodies** — that is where a password would end up in the journal (R-SEC-10)
- [ ] The generated file carries a header comment saying it is generated, by what, and that edits are lost on the next apply.
- [ ] `renderer.ts`: `ConsoleRenderer implements Renderer`. `render(config)` writes `settings.js` with `writeFileDurable`, then restarts `yonder-console.service` through the injected `CommandRunner`. It must **never** restart `yonder-core`.
- [ ] A console that fails to restart must fail the render — so an unconfirmed apply rolls it back — but must not be able to leave the *network* renderer's work reverted in a way that drops the access point. Follow whatever ordering `buildRenderers` already establishes for `NetworkRenderer` and put the console **after** it, so the network is settled before the console is touched.
- [ ] Register `ConsoleRenderer` in `buildRenderers` so `ui.*` changes go through apply/rollback.

**Tests:**
- [ ] `renderSettings` output contains `functionExternalModules: false` and excludes the function node — asserted directly, because this is CLAUDE.md rule 2 expressed in code and it must fail loudly if someone removes it.
- [ ] Unprovisioned output has `httpAdminRoot: false`; provisioned-with-editor-disabled also has `false`; provisioned-with-editor-enabled has the admin root and an `adminAuth`.
- [ ] The port comes from config, not a constant.
- [ ] The output contains **no secret and no password hash** — assert on the string.
- [ ] `ConsoleRenderer` restarts only `yonder-console.service`; a test asserts the runner was never called with `yonder-core`.
- [ ] A failing restart surfaces as a render failure.

**Verify:** `npm test`

## Exit criterion

On this machine, with no hardware: a daemon and a console start from a clean root, the console serves exactly one page and refuses everything else, an administrator password can be set once, the console restarts into a login gate, and the flow editor is unreachable without that password. The journal contains no copy of the password.

**This does not close M1.** M1's own exit criterion needs the pages M1b-2 builds and the cold boot M1a still owes.
